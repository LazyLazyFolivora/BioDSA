# 推理过程可视化 — 难点分析

## BioDSA 侧

### 难点 1：Agent 推理信号→结构化事件的实时转译

**背景**

DeepEvidence agent 采用 orchestrator + BFS sub-agent + DFS sub-agent 三级结构。运行时 `agent_graph.stream()` 以 `subgraphs=True` 模式产生 chunk，每个 chunk 来自不同层级的 agent。提取器需要在流式处理中正确识别每条消息的来源，并映射为对应的叙事事件。

**技术要点**

事件有三个来源，性质和时机不同：

| 来源 | 发生时机 | 内容 | 确定性 |
|------|---------|------|--------|
| KB 工具 tool_calls | agent 调搜索工具时，即时 | agent 准备查什么实体 | 高（结构化 args） |
| AddToGraph 写入 | orchestrator 分析完毕后，延迟 | agent 确认了什么实体和关系 | 高（结构化 args） |
| Phase 切换 | orchestrator 调 BFS/DFS 工具时 | 当前研究阶段 | 高 |

subgraphs chunk 结构下，BFS agent、DFS agent、Orchestrator 各有不同的可用工具集。extractor 需要维护 `agent → tools → event_type` 的映射，才能正确判断每条 tool_call 产生什么事件。

**关键问题**

KB 工具的 entity_type 和 AddToGraph 的 entity_type 使用两套命名体系（如 `"gene"` vs `"GENE"`），需要归一化处理后端才能返回一致的类型标识给前端配色体系。

---

### 难点 2：同步 agent 执行下的实时事件推送

**背景**

`agent.go()` 是同步阻塞函数，单次运行 3-5 分钟。但 MCP tool handler 声明为 `async`，如果不做处理，同步调用会阻塞 Starlette 的事件循环。

**技术要点**

- 使用 `run_in_executor` 将 `agent.go()` 丢入线程池执行，释放事件循环处理其他请求
- 广播器 `emit_sync()` 需要在多线程环境下安全地写入 asyncio.Queue（`put_nowait` 是线程安全的）
- 线程池大小需要限制，防止多用户并发时 vLLM 的并发上限和显存被打爆

**关键问题**

多 agent 实例同时运行时，共享的 LLM 后端（vLLM）存在并发上限。需要在 MCP Server 层做好线程池限流，避免 OOM 或请求堆积。

---

### 难点 3：图谱数据的生命周期管理

**背景**

当前证据图（evidence graph）在每次 `go()` 调用入口处清空，运行结束后也不保留。引入 session_id 后需要改为：

- 每个 session 使用独立的 evidence_graph_name，互不干扰
- agent 运行中：broadcaster 持续推送增量事件
- agent 结束：推送 RunComplete 事件，携带 `load_graph_data()` 的完整图谱快照
- agent 崩溃：finally 块中清理 broadcaster 的 Queue，防止资源泄漏

**技术要点**

`load_graph_data()` 已提供 `{entities, relations, observations}` 的结构化导出，可直接作为 RunComplete 事件的 payload。不需要额外序列化逻辑。

## WeKnora 侧

### 难点 4：在现有事件体系上扩展图谱事件通道

**背景**

WeKnora 已有完整的事件流基础设施：`EventBus`（per-request 发布订阅）→ `AgentStreamHandler`（订阅转发）→ `StreamManager`（Redis 队列）→ 前端 SSE。现有事件类型包括 `thought`、`tool_call`、`tool_result`、`final_answer`、`references`、`complete` 等。

**技术要点**

新增 `graph_event` 事件类型需要贯穿三层：
1. `event.go` 定义事件类型和数据结构
2. `AgentStreamHandler` 订阅并转发
3. 前端 SSE 消费端增加 `graph_event` 处理

关键约束：新增事件不能破坏现有事件的处理逻辑。AgentStreamHandler 的 per-request EventBus 天然隔离了不同用户的事件流，不存在串流风险。

---

### 难点 5：MCP CallTool 阻塞期间并行读取进度流

**背景**

`MCPTool.Execute()` 调用 `client.CallTool()` 时阻塞 3-5 分钟。图谱事件需要在这个阻塞期间实时推送给前端。

**技术要点**

- 在 `CallTool` 调用前启动 goroutine，并行连接 BioDSA `/progress?session_id=xxx`
- goroutine 读取 SSE 事件 → `EventBus.Emit(EventAgentGraph)` → 通过现有链路推给前端
- `CallTool` 返回后（或 SSE 收到 `RunComplete` 事件时）终止 goroutine

**关键问题**

- goroutine 生命周期管理：agent 正常结束、异常崩溃、CallTool 超时——三种场景下 goroutine 都需要正确清理，不能泄漏
- SSE 连接断开时的重试策略：短暂网络波动后自动重连，利用 broadcaster 的环形缓冲区补回丢失的事件

---

### 难点 6：图谱持久化与历史回显

**背景**

用户关闭对话后再次打开，图谱需要从存储中完整恢复——不能要求 agent 重新跑一遍。图谱属于对话产物，应由 WeKnora 侧存储。

**技术要点**

- 新增 `biodsa_graph_snapshots` 表，以 session_id 为主键，graph_data 存完整 JSON
- 写入时机：前端收到 RunComplete 事件后调 `POST /api/biodsa/graph/snapshot` 落库
- 读取时机：前端加载历史对话时，根据消息中的 session_id 调 `GET /api/biodsa/graph/{session_id}` 恢复图谱
- Cytoscape.js 状态恢复不仅是数据结构（节点、边），还包括渲染状态（节点位置、布局参数、缩放层级）

**关键问题**

图谱 JSON 大小——复杂研究问题可能产生 50+ 实体和 100+ 关系。需要确认 PostgreSQL JSONB 的存储和查询性能在此量级下无瓶颈。

---

## 难度汇总

| 序号 | 难点 | 侧 | 本质 |
|------|------|----|------|
| 1 | 推理信号→结构化事件转译 | BioDSA | 语义映射 + 流式处理 |
| 2 | 同步执行下的实时推送 | BioDSA | 并发模型 + 线程安全 |
| 3 | 图谱数据生命周期管理 | BioDSA | 资源隔离 + 异常清理 |
| 4 | 事件体系扩展 | WeKnora | 已有系统上的零破坏扩展 |
| 5 | 阻塞调用期间的并行读取 | WeKnora | goroutine 生命周期管理 |
| 6 | 图谱持久化与历史回显 | WeKnora | 存储设计 + 状态恢复 |
